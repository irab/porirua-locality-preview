Data pipeline & geo fixes

Build: npm run build:data — FSD import → Porirua filter → merge with Connections Map → services.json.

  • Recent work reduced false positives in the FSD slice (address-context filter, exclusion audit)
  • Review data/fsd-porirua-excluded.json reason codes after each refresh
  • overrides.json — hide or patch rows without a full rebuild workflow
  • Community row wins on dedupe (name + map coordinates); FSD duplicate hidden
Not fixed by geo work: large NGOs still appear as many similar cards — FSD is one row per service line (see org gap slide).

Docs: MVP-RUNBOOK, fsd-porirua-filter-rationale, issues directory

Geocode QA workflow

After inclusion, import runs post-filter geocode QA on FSD rows that made the slice.

  • Flags suspicious coordinates (e.g. offshore Kapiti/Cook Strait box, out-of-bounds)
  • Output: data/fsd-porirua-geocode-flags.json (regenerated, gitignored)
  • Editors cross-check flagged rows before publish — map pins depend on good lat/lng
  • Script: fsd-geocode-qa.mjs + unit tests in pipeline
StepAction

FixOverride hide/patch or upstream FSD correction
PublishCommit services.json when satisfied

Org / subservices gap

Largest product vs data mismatch from MVP testing.

Users expectOne organisation → list of offerings (Connections Map grain)
FSD providesOne CSV row per service line — repeated provider text
Phase 1 UIOne card per FSD row; duplicate slugs possible (e.g. Salvation Army Porirua ~13 cards)
  • Dedupe is community vs FSD only — not FSD-vs-FSD grouping
  • Directory is trustworthy for “something exists in Porirua” but can feel repetitive
Fix needs product choice: Phase 1.5 stable service ids → Phase 2 org hierarchy + grouped UI (~1–2 weeks UX-dependent).

Accessibility (target)

Public resource for people under stress — aim for high practical accessibility, not a compliance claim today.

Phase 1 shippedSkip link, landmarks, aria-live results, labelled favourites, print-friendly My list
GapNo formal WCAG audit, axe gates, or assistive-technology test programme
Phase 1.5WCAG 2.2 AA baseline on public pages; fix critical/serious audit findings
Phase 2AA everywhere users transact; map as enhancement with list-first alternatives

Budget accessibility explicitly in 1.5/2 — comparable importance to accurate data.

Phase 1.5 & Phase 2

Phase 1.5 — pipeline quick win

  • Public id from SERVICE_ID / FSD_ID; optional service titles on cards
  • Still many cards per large org — minimal UX change

Phase 2 — product & admin

  • Org grouping + subservices in UI and schema
  • Directus admin, weekly FSD automation, Squarespace embed
  • Duplicate linking UI, formal WCAG pass, near-me product decision

Deferred: Te Reo labels, PWA, analytics — see requirements §9–10

Open questions for discussion

  1. One card per service vs one org with expandable offerings?
  2. Card title: organisation name, service name, or both?
  3. Stricter regional FSD filter vs manual hiddenIds?
  4. Literacy / multi-site FSD naming — accept, override, or wait for org grouping?
  5. Editor workflow: Sheet + developer merge until Directus — acceptable?
  6. When community and FSD match, always hide FSD — or show service lines under org in Phase 2?
  7. Search subservices — Phase 2 only or enough provider-name search in 1.5?
  8. Map-first handoff: clear filters (recommended) vs preserve map/chip context?
